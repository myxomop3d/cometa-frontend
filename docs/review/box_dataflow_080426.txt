
● Box Dataflow Review — Senior React Reviewer Findings

  Critical bugs (fix first)

  1. Wire-shape mismatch — onSubmit ships flat {itemId, thingIds, oldItemId, oldThingIds} to patchBox/createBox, but they're typed Partial<BoxDto> (which has nested item, things). TS passes only because of structural overlap. Backend either rejects or silently drops relations. -box-sheet.tsx:106,109 ↔ api/box.ts:98,269.
  2. PATCH is a PUT in disguise — entire form sent every time. Use form.formState.dirtyFields to build a partial payload.
  3. oldItem* likely audit fields — almost certainly server-managed history; making them user-editable via RelationPicker lets editors forge audit history. Confirm with backend; probably remove from form entirely.
  4. createBox swallows HTTP errors — no res.ok check, returns error envelope as BoxDto, try/catch never fires → "Box created" toast on failure. Same flaw in boxDiceQueryOptions.queryFn. Mirror fetchBoxes/patchBox pattern.
  5. rowAction typing — { row: null as any, variant: "create" } (index.tsx:237). Model as discriminated union: {variant:"create"} | {variant:"update"; row}.
  6. Sheet variant flicker on close — rowAction?.variant === "create" ? "create" : "update" flashes "Edit" during close animation when state is null.
  7. getBoxColumns useMemo deps wrong; loader rebuilds throwaway columns just to harvest filter meta — extract a pure boxFilterDescriptors constant.

  Direct answers

  Q2 — Separate BoxForm type or reuse BoxDto? Separate. They're genuinely different models: BoxDto is the read shape (nested relations, audit fields), BoxFormValues is the edit shape (flat IDs, no audit), and you also need a third BoxWritePayload for the wire. Reusing Partial<BoxDto> is exactly what produced bug C1. Cost: one mapper file. Benefit: compiler enforces the boundary.

  Q3 — Centralize types + zod schemas? Yes — but co-locate by feature, not by kind. Schema living inside the sheet is what made it invisible to the API layer. Recommended:
  src/features/box/
    schema.ts     # zod + BoxFormValues + BoxWritePayload
    mappers.ts    # boxDtoToForm, boxFormToCreate, boxFormToPatch
    api.ts
    columns.tsx
    components/BoxSheet.tsx
  Keep src/types/api.ts as DTO-only (wire contract). Don't dump form schemas there.

  Q4 — DTO ↔ Form mapper? Unconditional yes. The mapping is already duplicated between defaultValues and the useEffect reset (8 identical lines that will drift). And you need boxFormToWritePayload(values, dirtyFields?) to fix the bugs above anyway. Once extracted, the sheet shrinks and the mapper is unit-testable without mounting the component.

  Q5 — Generic reuse (without over-engineering). You already have most of the pieces; they just need to grow up. Order, by dependency:

  1. Extract buildDataTableParams from box.ts → src/lib/odata/build-filter-params.ts. It's already pure and generic; it's just trapped in the wrong file. Zero risk. Do this first — it's the single clearest signal that a pattern is forming.
  2. createCrudApi<TDto, TFilters, TWritePayload>(basePath) factory returning {fetchList, fetchOne, create, patch, delete, listQueryOptions, detailQueryOptions, dataTableQueryOptions}. This is what your api-layer agent is hinting at — don't write four more box.ts clones.
  3. useEntitySheet({schema, dtoToForm, formToCreate, formToPatch, api}) hook owning form + dirty tracking + mutation + error mapping. Visual <EntitySheet> wrapper takes a render-prop for fields.
  4. createEntityRoute({api, columns, searchSchema}) — box-dice/index.tsx is 258 lines, ~90% would repeat for the next entity. Goal: ~50 lines.

  Don't abstract yet: schema-driven form rendering (wait until 3rd entity proves field-type repetition), or a relation-picker config DSL (RelationPicker is already generic enough). Concrete next move: lift buildDataTableParams, then build entity #2 by copying box.ts as a template — the friction you feel writing #2 tells you which abstraction is actually worth extracting. That's the disciplined path; building the framework upfront ossifies the wrong shape.
