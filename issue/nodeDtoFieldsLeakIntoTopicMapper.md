# A field added to `NodeDto` is silently inherited by `TopicMapper`

Found 2026-09-23 by the whole-branch review of the Node→TechComponent link
work. The specific instance was fixed in backend `a160bfc`; the structural
hazard remains and will recur.

## Problem

`TopicDto extends NodeDto` and `Topic extends Node`, so `TopicMapper` — a
mapper declared in its own file, which no task in that work touched — is
regenerated by MapStruct with every new `NodeDto` property. Adding
`techComponentLinks` to `NodeDto` gave `TopicMapperImpl` two defects at once,
neither visible in any per-task diff:

- a write fallback, `target.getTechComponentLinks().clear()` then refill, on a
  lazy setter-less inverse collection — the same defect that had just been
  fixed on `NodeMapper` one commit earlier;
- an unguarded nested read: `TopicMapper`'s `uses` did not include
  `NodeTechComponentLinkMapper`, so MapStruct generated a local mapping method
  with no `@Condition`, and `GET /api/v1/topic?$fields=techComponentLinks`
  returned a populated `techComponent` where `/node/graph` with identical
  `$fields` returned `null`.

Six per-task code reviews saw only their own diffs and could not detect this,
because `TopicMapper.java` appears in none of them. Only a whole-branch review
reading the **generated** sources found it.

## Related gap

`TopicMapper.fromDto` / `update` still have **no JUnit regression test**. The
guarantee that the write path stays shut rests on grepping generated sources,
which is not part of `mvn test`. A future edit removing `@IgnoreNodeLinkedObjects`
from `TopicMapper` would pass CI. Latent today only because
`TopicRestController` exposes reads only.
